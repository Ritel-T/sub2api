# Database backup integrity

New single-object backups record the compressed archive's SHA-256 and byte size in the application's backup record before upload. Split backups retain a SHA-256 and size for every part. Both synchronous and background restores first download the bounded objects to a private temporary file, verify every recorded digest and size, and only then decompress or send SQL to PostgreSQL. A mismatch or missing integrity metadata prevents automatic restore; partial downloads are removed.

Historical backups without a valid recorded digest remain listed and downloadable, but automatic restore fails with `BACKUP_INTEGRITY_UNAVAILABLE`. Keep those objects and their existing records. For recovery, download them through the existing administrator download action, establish provenance against an independent trusted copy or previously recorded digest, inspect and rehearse recovery in an isolated database, then perform an explicitly authorized manual restore. Calculating a hash of today's object does not prove that the object matches the original backup; do not backfill that hash and label it verified. Create a new backup to obtain a fully verifiable current recovery point.

The digest stored in the application database protects against modification by a party that can replace backup objects but cannot modify application records. It does not authenticate an attacker-controlled database and object store together. Versioning, immutable storage, separate writer permissions, and independently retained recovery material remain useful additional controls. Verification requires local temporary disk space equal to the compressed archive and adds a full read before any database writes.
