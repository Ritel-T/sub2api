# DeepSeek 实时自动恢复

实现状态：本地开发与验证，未发布。基线 `2645513a108d2b19e241c6c97ff444f52139464b`，包含已上线 2.18.0.27 的原生账号模板与此前增量。本功能不修改渠道配置或重新启用停用渠道。

## 已对齐的目标

保留实时输出，提高一次请求最终完成的概率，减少用户手动重试。用户已接受：文本或思考中途失败时提示“上游中断，正在重新生成”，自动换渠道从头生成，因此最终回复可能保留重复内容和增加等待。

此前 REALTIME-V3 的“所有业务提交后都不重试”方案已由本合同替代；完整答案缓存方案也不采用。

## 覆盖范围与行为

- 首版覆盖 DSH 实际使用的 Chat Completions 与 Anthropic Messages HTTP 入口，流式和非流式均支持。仅在请求平台为 DeepSeek、模型名为 `deepseek-*`、单 choice、没有 `previous_response_id` 时接入。
- 初次选择沿用现有调度；失败后从原组其他可用渠道随机选择，忽略账号粘性、parent、软优先级和 TopK。模型/组权限、启用状态、配额、利润与并发准入继续生效。
- 最多 3 个不同渠道、每渠道至多一次实际推理提交。恢复阶段预算 10 分钟；单尝试最多 5 分钟、首次业务内容和业务停顿各 120 秒。此前用户准入排队与最终账务收尾沿用原合同。上游心跳不能延长绝对预算。这些是有界恢复的初始值，未经生产延迟分布标定，不承诺适合所有百万上下文任务。
- 上游 HTTP 错误、200 内错误、错误协议、无效响应、缺终态、资源不足/aborted、只有思考没有答案，均可在预算内换渠道。源协议校验发生在转换之前，避免把失败映射为正常结束。
- 正文和思考逐事件立即 flush；只暂存起始元数据和最终结束/用量事件，失败尝试不提前向客户端发送错误或结束信号。
- 中途文本失败时保留已发内容；新渠道开始输出后添加中文重试分隔提示。整个请求使用一个下游响应身份，Messages 内容块索引连续，不把第二个独立 response/message 信封直接拼进去。
- **工具调用事件一旦尝试写给客户端，就禁止重放。** 避免客户端已执行工具后重复执行；不伪造工具完成、成功终态或自动续写。空文字但有完整工具调用属于有效结果。
- **结构化 JSON 输出只在业务输出前恢复。** 已开始后不插入重试文字破坏 JSON。正常 `length/max_tokens` 且有答案保留原截断语义；输出预算不足不能通过换号偷改大。
- 客户取消、租约丢失、下游写失败立即停止重试。失败旧尝试的真实 HTTP/Body 被取消关闭，账号槽位释放后再开始下一次。
- 网关每 15 秒发送无业务语义的 SSE 注释保活，写入与业务帧串行。非流 JSON 不发送心跳。HTTP200 心跳提交后，最终失败使用对应协议的流内错误。

Responses、WebSocket、Search/Fetch 工具桥、其他厂商、多个 choice，以及依赖账户专属状态的续接，不在本次自动恢复范围内，继续沿用现有流程。

## 计费与观测

用户/Key 准入、RPM、在途余额预留和计价时间只建立一次。每次转发使用独立 Gin 状态，旧失败的错误标记、模型观测和 cyber 后台收费旁路不能进入下一个尝试。

上游 `cyber_policy` 仍执行既有的安全审计、通知和已配置会话策略，每个逻辑请求一次；恢复协调器只禁止其独立失败收费分支。本轮可按用户要求继续尝试其他渠道，后续请求仍受站点原有会话策略约束，与现有 WebSocket 换号期间保留风控标记的合同一致。

只向既有客户计费入口提交最终选定结果的一份命令，保留其真实账号、上游模型、token/cache 明细、公开模型、分组与倍率。已暴露工具或客户端断开时，有可确认的部分用量仍沿用现有部分计费合同；可重试而被丢弃的失败文本尝试不生成客户账单。未知用量标为 unavailable，不伪造零用量成功。

失败尝试的安全用量快照进入现有 Ops 明细，供应商实际金额没有证据时标为 unknown。此版本不新建供应商财务账本、不对用户自动退款、不把失败用量伪装成零元客户账单，也不自动以估算金额回写失败账号的成本配额。供应商可能仍收取失败尝试费用，运营成本可能增加。需要供应商精确成本/失败账号额度对账时，以这些明细和供应商账单另行核对。

结算错误只沿原持久账务恢复链处理，不重新请求模型。服务器的一次请求与客户端自行发送的新 POST 是两次请求，本功能不提供跨 POST 去重或断连后答案重取。socket 交付与数据库结算不能成为同一原子事务，不承诺“用户实际看到答案才会扣费”。

## 验证方式

测试使用本地可控上游、合成请求与虚拟凭据，没有向生产模型发请求。

- 实际两个 handler 的失败→成功路径：HTTP400、200 error、半流 EOF、resource finish、reasoning-only；不同账号、只有一个正常结束、只有一份最终用量。
- 三次上限、不回旧账号、取消、图片/输出预算保持、完整工具、已暴露工具后断流、结构化 JSON 与正常长度终止。
- 常规 durable 计费的真实命令构建与 Stage/Apply 接口：A已有用量但失败，只Stage B一次；Apply失败不再生成。使用内存仓库替身，不冒称真实钱包/数据库验收。
- 源协议 CC/Anthropic/Responses 校验、超时、租约取消、单发送约束；重试选号复用硬门、跨组拒绝、80候选不受TopK截断、忙闲槽位和粘性保持。
- 并发检测覆盖源读取/取消、心跳和流写入。保留相关原有转发回归。
- 用 DSH `0.2.1-rc.2` 安装包自带 Pi-AI `1.4.0` 解析实际 handler 生成的流，两个协议各验证半流断开、纯思考、资源不足后恢复。fetch完全被本地替身截获，验证的是客户端解析行为；没有冒称完整 DSH 界面或自然生产链路验收。

源码分工：`handler/deepseek_recovery.go` 控制一次请求；`deepseek_recovery_stream.go` 管理下游信封与交付；`service/deepseek_recovery_attempt.go` 控制真实上游发送、生命周期与源结果；`deepseek_recovery_selection.go` 复用既有硬门选号；`deepseek_recovery_observation.go` 记录失败尝试。
